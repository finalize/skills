# 決めごととしての仕様

既定のまま「仕様を書いて」と頼むと、振る舞いを網羅した長い説明になり、曖昧な点は黙って決められ、
「適切に処理する」「正しく扱う」のような何も言っていない文が混ざる。実装が始まると、決めていなかった点は
実装の都合で埋まり、README よりコードが正になる。

仕様に書くのは**決めごと**だけ。どちらでもあり得た中で選んだほうと、その理由。説明や網羅は書かない。

## 順番

1. **目的を一文で書く。** 誰が使い、何が変わるか。後の決めごとはこの一文に照らして選ぶ。
2. **決めごとが隠れている場所を順に探す。** 要件の一文ごとに次を聞く:
   - 優先順位: 2つの条件が同時に成り立つとき、どちらが勝つか
   - 境界: 端が接するとき、0件のとき、同時刻のとき、上限ちょうどのとき
   - 不正な入力: 長さ 0、0 や負の値、逆順、空の名前、同じものを二度指定。断るか、直して受けるか
   - 同じものの別表記: 大文字と小文字、前後の空白、全角と半角。同じとみなすか、別とみなすか
   - 取れないとき・途中で止まったとき: 何を返し、何を残すか
   - 時刻と地域: どの時計か、「今」を誰が知るか、過去や未来を受けるか、日付をまたぐとき、週の始まり
   - 二度やったとき: 同じ操作をもう一度、取り消した後にもう一度
   - 見え方: 並び順、取り消したものは出るか、過去のものは出るか
   - やらないこと: 要件にありそうで、意図して置かないもの
   聞いた答えを要件の一文ごとに1行ずつ書き出してから清書する。頭の中で済ませると飛ばす。
3. **1つの決めごとに1つの例を付ける。** 具体的な値で。例が書けない決めごとは曖昧なので、書けるまで削る。
   この例がそのままテストの一覧になる。
4. **決められない点は決めない。** 目的の一文から導けないもの、使う人の好みで変わるものは
   「要確認」に質問の形で残す。埋めたくなるが、埋めた瞬間に実装の都合が仕様になる。
5. **既存のコードから起こさない。** 目的・呼び出し元・使う人から見た振る舞いから書く。コードを読んで補った箇所には
   「（実装から）」と印を付ける。コードから起こした仕様はコードのバグを引き継ぐ。
6. **置き場所はコードの外。** README か docs。冒頭に「食い違ったら仕様が正」と一文書く。
   関数のコメントに書いた意図は、コードの一部として読まれて負ける。
7. 出口は完成した文書ではなく、**決めごとの一覧＋例＋要確認の一覧**。要確認を人に返し、答えが来たら決めごとに昇格させる。
8. **出す前に見直す。** 次のどれかに当たったら直してから出す:
   - 例の無い決めごとがある
   - 決めごと同士、または「やらないこと」と決めごとが食い違っている
     （「正の数だけ」と言いながら負の例を出す。片方で持たないと言ったものを、もう片方で返す）
   - 「適切に」「正しく」の類が残っている
   - 要件の文で、決めごとにも要確認にも落ちていないものがある
   - 要件にも目的にも無い制約を足している（「金額は 100 円単位」など）。足したくなったら要確認に回す
   - 要確認が 0 件。数行の要件で決められない点が無いことは、まず無い

## 書き方

- 1決めごと1行。「〜する」と言い切る。理由は括弧か次の行に
- 使わない言葉: 適切に、正しく、必要に応じて、基本的に、できるだけ、柔軟に。書きたくなったら例に置き換える
- 数える。上限・件数・日数・桁は数字で。「十分に速い」は決めごとではない
- 要件をそのまま写さない。「重なった予約はできない」は要件で、「端が接するのは重ならない」が決めごと
- 試して決めたものは数字ごと残す（0.03 と 0.05 を実測して 0.03 にした、など）
- 長さの目安は決めごと5〜15行。それ以上あるなら、説明が混ざっているか、決めなくていいことを決めている

## 形

```markdown
# 本の貸し出し

目的: 家族で共有する本を、誰が持っているか口頭でなく記録で分かるようにする。

食い違ったら、この文書が正。

## 決めごと
- 期限は借りた日の14日後の日付。時刻は見ない（返すのは日単位なので）
- 延長は1回まで、期限の前日まで受け付ける。延長後の期限は元の期限の14日後
- 貸出中の本は借りられない。待ちの列は作らない（家の中なので声をかければ済む）
- 一覧は期限の昇順。同じ期限なら題名順

## やらないこと
- 延滞の通知。一覧の上に来るので見れば分かる

## 要確認
- 返した直後に同じ人が同じ本を借り直せるか
- 期限を過ぎた本を持っている人は、別の本を借りられるか
```

## このスキル自体を確かめたこと（2026-09-23）

要件を数行だけ書いた依頼を渡し、「実装する前に SPEC.md を書け」と頼んだ。各題材に曖昧な点を7つ仕込み、
決めごとか要確認として触れた数を数えた。別プロセス、スキル無しは本人が「一覧に無い」と確認。

**会議室の予約**（端が接する予約、取り消し後の再予約、取り消したものが一覧に出るか、並び順、開始≥終了、過去の予約、同じ人の二重予約）

| モデル | スキル | 行数 | 7点のうち触れた | 要確認 | 備考 |
|---|---|---|---|---|---|
| Claude Haiku 4.5 | 無し | 90 / 68 | 3 / 2（理由なし） | 0 / 0 | 型と API の説明書。「適切にロックする」 |
| Claude Haiku 4.5 | あり・初版 | 30 / 30 | 4 / 4 | 3 / 4 | 開始≥終了と過去を2本とも落とす。1本に矛盾 |
| Claude Haiku 4.5 | あり・直し後 | 30 / 29 / 30 | 5 / 7 / 6 | 2 / 6 / 4 | 矛盾なし |
| Claude Fable 5.1 | 無し | 191 / 209 | 6 / 6（理由つき） | 1 / 5 | 用語・API・受け入れ条件まで含む設計書 |
| Claude Fable 5.1 | あり・初版 | 56 / 49 | 6 / 6（例と理由つき） | 6 / 3 | |

**家族の支出の月次集計**（直した後に、別の題材として。月の境界、直した記録の履歴、二度登録、負や 0 の金額、並び順、記録の無い月、分類の表記ゆれ）

| モデル | スキル | 行数 | 7点のうち触れた | 要確認 | 備考 |
|---|---|---|---|---|---|
| Claude Haiku 4.5 | 無し | 51 / 47 | 0 / 2 | 0 / 0 | API の説明書。「検討項目」に実装の話だけ |
| Claude Haiku 4.5 | あり・1回目の直し | 35 / 33 | 6 / 4 | 4 / 4 | 2本とも金額の符号で自分と矛盾 |
| Claude Haiku 4.5 | あり・2回目の直し | 34 / 38 / 37 | 6 / 5 / 4 | 5 / 5 / 4 | 矛盾なし。1本が頼まれていない制約（100 円単位）を足した |

- 弱いモデルでは、無しだと決めごとも質問も無い API 仕様書になる。ありだと決めごと＋例＋やらないこと＋要確認の形になり、
  触れる点が 0〜3 から 4〜7 に増え、曖昧語が消える。
- 直しの経緯: 落とした点を「探す場所」に足し（不正な入力、今を誰が知るか、0 や負、別表記）、
  見直しに「決めごと同士の食い違い」を足した。直した後は落とした点を拾い、矛盾は消えた。
  最後に足した「頼まれていない制約を足さない」は、足した後に測っていない。
- 強いモデルは無しでも同じ点を理由つきで決め、質問も出す。スキルの効き目は長さが 1/4 になり、決めごとだけになること。
- 本数は各条件2〜3本。傾向どまり。
