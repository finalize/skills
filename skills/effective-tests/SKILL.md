# 効くテストの書き方

LLM のテスト生成は「実装を読ませて、今の実装で通るテストだけ残す」作りになっている。残るのは**今の振る舞いの写し**で、
正しいプログラムも間違ったプログラムも同じように通す。バグ入りのコードに対して生成された組の 60〜68% が
「バグを通し、直すと落ちる」テストだった（Mathews & Nagappan 2024）。バグ入りのコードを見せると、それを是とする
テストが増え、暴くテストが減る（Zhao et al., ISSTA 2026）。エージェントは落ちたテストを、期待値の書き換え・入力の特別扱い・
skip の追加・モックを検証するテストで「通す」ことがある（Anthropic / OpenAI / METR の報告）。

だからテストの役目は**仕様の固定と退行の網**で、実装の検算ではない。**「今の実装で通る」は受け入れ条件にならない。**

## 順番

1. **書く前にテストの一覧を作る。** 仕様・README・設計の判断の一文を1ケースにする（Beck, Canon TDD の第1手）。
   実装を読んで「この `if` を通す入力」を並べない。
2. **実装が間違っているかもしれないなら、実装を読む前に書く。** 仕様だけを見る（ISSTA 2026）。
   README も docstring も無ければ、**先に仕様を一段落書く**（関数名・呼び出し元・コメントから「何をするはずか」）。
   それをテスト一覧の元にし、実装を開くのは型と名前を知るためだけにする。
   曖昧な点は推測で埋めず、テスト名に「（要確認）」と付けて人に返す。
   自分が実装した直後なら、実装の文脈を持たない別のエージェントに**仕様だけ**渡して書かせる
   （Claude Code なら Agent ツールで新しい文脈を作れる）。
3. 決めごとが先にあるなら落ちるテストを先に書き、**どう落ちるか予想してから走らせる。** 予想と違う落ち方はテストの間違い。
4. **落ちたら実装を疑う。** テストを変えてよいのは3通りだけ（North）:
   バグを入れた → 実装を直す／振る舞いが別の場所に移った → テストを移す／前提が変わった → テストを消す。
   期待値を変えるなら、理由をコミット本文に書く。
   既にあるテストが仕様と矛盾するなら、間違っているのがテストのこともある。仕様を正として、どちらを直したかを書く。
   実装を直すのが依頼の範囲外なら、**落ちたままにして食い違いを報告する。** テストを実装に合わせて通すのは駄目。
5. **やってはいけない通し方:** 期待値の書き換え、テスト入力の特別扱い、assertion を弱める、skip を足す、
   スナップショットの更新、モックを検証するテスト。問題が不合理なら、直さずにそう言う。
6. **通ったら一度壊す。** 守っているつもりの条件（照合、境界、分岐）を**実装の側で一時的に**外して走らせ、
   落ちるのを見てから元に戻す。テストファイルに「壊れていないか見る」テストを足すことではない
   （`t.Logf` で警告を出すだけのテストは何も守らない）。
   **落ちないテストは守っていない。** ログ・タイムアウト・調整用の定数を変えて落ちなくても、それは相手にしない変異。
7. 偽物と本物のずれは contract test で見る（Fowler）。無理なら手で通し、日付と結果を README に書く。テストには入れない。

## 固定するもの

- **設計の判断。** どちらでもあり得た中で選んだほうを1ケースにし、コメントに「ここが設計の判断」と理由を書く
- **外部仕様は出典の参照値。** 定数を推測せず、RFC のテストベクタなど公表値を出典 URL つきで固定する
- **実際に壊れた入力。** 直す前に、壊れていた入力で落ちるテストを書く。いつ・どこで壊れたかも書く
- **優先順位は表。** 「A より B が先」は実装の写しが一番取りこぼす。表はデータだけを持ち、テスト側に分岐を書かない
- **取れないときの契約。** 情報源が落ちても結果は返る、空は `nil` でなく空、「500 が返った」と「繋がらない」を分ける、
  キャンセルは途中までの結果が返ること・その後続けていないことの両側から
- **保存形式はファイルの中身を読む。** 往復だけでは何が書かれたか分からない
- **同じ値が複数箇所にあるなら一致を見る。** 片方だけ直すとずれるもの
- **実装を写せない形。** 順序に依らない、行って戻る、2度やっても同じ、別の実装と照らす、出力の全部が条件を満たす、
  並行の両側（上限を超えない かつ 本当に並行している）、返ってくること
- **描画・出力も性質で。** 幅の規則、色あり／なしで桁が揃う、画像は描いてから塗られた割合を数える

## 書かないテスト

- 組み立てたリクエストをモックから読み返すだけのもの。残すなら「無いと何が起きるか」をコメントに書けるときだけ
- モックを検証するテスト
- 弱い assertion（`not null`・`例外が出ない`・`length > 0` だけ）。何もしない変異を通す
- 出力全体のスナップショット。画像の比較は「出力そのものが色」のときだけ
- 1テストに複数の振る舞い（どの assertion で落ちたか分からない）
- private や実装の詳細。公開 API 越しに試す
- 環境で変わる値の決め打ち（週の始まり、ロケール）
- 現在時刻・`sleep`。今日は引数、時計は関数で注入、待ちは偽の時計（Go `testing/synctest`、JS `vi.useFakeTimers()`）

## 外に出ない

小さいテストは**1プロセスで、sleep も I/O もブロッキングもしない**。ネットにも画面にも実機にも本物の設定にも出ない。
出たくなるもの（HTTP、環境変数、時計、ファイル、設定の保存先、入力イベント、画面、乱数、署名、DB）は
seam で差し替える。差し替えるのは**管理外の依存**だけで、自分で管理している DB やファイルは本物か fake を使う。
署名の検証はモックにせず、鍵を作って本物の署名で試す。対応表と形は `reference.md`。

## 走らせ方

- 1コマンドで全部走る。CI も同じコマンドを叩く。テストは実装と同じ PR に入れる
- 揺れるテストは直すか隔離する。揺れが 1% に近づくと組全体が信用を失う
- 画面を持たない本体を分け、シミュレータもブラウザも無しで走らせる。本体にファイルを足したら、テストの対象にも足す
- 測るなら網羅率でなく変異スコア。ただし意味を持つのは本体が正しいと言えるときだけ
