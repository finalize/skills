# 証拠で直す

既定のままだと、AI は不具合の報告を読んでコードを開き、もっともらしい原因を1つ決めて直し、テストかビルドが通ったら
「直しました」と言う。報告に添えられた見当（「〇〇が怪しい」）を、そのまま原因として扱うこともある。
直ったかどうかは、報告した人が同じ画面をもう一度開くまで分からない。

このスキルは、直す前に同じ面で再現することと、直した後に同じ面で消えたのを見ることを、終わりの条件にする。

## 向くとき・向かないとき

- 向く: 画面・挙動・遅さの不具合。報告した人が見た面（スマホの幅、本番と同じ配信、実機、データ、打ったコマンド）があるもの。
- 向かない: エラーの文面が原因をそのまま言っているもの（型エラー、構文エラー、足りない依存）。直して同じコマンドを流せば足りる。
- かかるもの: 測った1件では、時間と費用が1.3〜1.4倍。結果は同じだった（下の「確かめたこと」）。

## 手順

### 1. 同じ面で、自分で再現する

報告した人が見た面で再現する。幅、配信のしかた（開発サーバーか、本番と同じ形か）、端末、データ、打ったコマンドそのもの。

- 自分で動かす。頼むのは、届かない理由を具体的に言えるときだけ（ログイン後の画面、本人の端末にしか無い状態）
- 人が使っている画面・実機・共有の環境には、合成の入力も壊す操作も送らない。試験用の窓、別のポート、別の作業ツリーで動かす
- 再現の手順は、後で同じものを流せる形（コマンド、スクリプト、撮る幅）で残す
- 再現しないなら、まず面が違うのを疑う。作った場面、別の起動コマンド、別の端末で通っていないか
- 応答が返っても、それがいま見ているコードの応答かを確かめる（別のプロジェクトのサーバーが同じポートで答えていたことがある）
- 再現しないまま直さない。条件を絞る・作る・ログを足すのどれかで、出るまで寄せる

### 2. 証拠で原因を絞る

- 見当は、自分のものも報告に添えられたものも、仮説の1つとして並べる。いちばん多くを切り分ける観測から先にする。
  手を入れるのは、切り分けた後
- 状態が分からないなら、ログや計測を足して、動いている最中に読む。推測で直さない
- 数字は、独立した別の源と突き合わせる。観測の手段が鈍いと「無い」「同じ」に見える
- いつから壊れたかが分かるなら、`git log -p` や `git bisect` で、壊したコミットを特定する
- 根本は、症状が出た場所ではなく、最初に間違った場所。そこで起きた状態が正当なら、壊れた側の扱いを直す。
  正当でないなら、その状態を作った側を直す。ガード、リトライ、握りつぶし、値の丸め、版の留めは、隠し方であって直し方ではない
- 再起動の後にだけ壊れるなら、保存された状態（設定、キャッシュ、ロックファイル）を先に疑う
- 同じ型の誤りがほかに無いか探す

### 3. 二度外したら、前提を確かめる

同じ前提に立った直しが2つ、同じ確かめで落ちたら、3つ目を書かない。
その前提を一文で書き、前提が間違っていれば結果が変わる観測を1つして、それから次に進む。
自分で作った土台（道具、クライアント、回避策）への手当てが続いているなら、その土台が前提になっている。

### 4. 証拠が支える分だけ直す

- 「念のため」の変更は仮説であって、直しではない。入れない
- 否定された仮説のために入れた変更は戻す
- 壊したコミットに意図があるなら、意図は残して壊れた所だけ直す。残せないなら、残せない理由を書く
- やむを得ず症状を止めるなら（版の留め、機能の切り替え）、外す条件と、外すのを忘れたときに何が起きるかを書く
- 本人の環境の設定のせいにして、設定を変えるよう案内しない。その設定のまま正しく動くようにする

### 5. 同じ面で、直ったのを見る

- 手順1の再現をそのまま流し、消えたのを見る。「たぶん直った」「別の面では通った」は、直ったと数えない
- 単体テストや UI テストが示すのは、作った場面での振る舞いで、不具合が消えたことではない
- 確かめが「直っていない」と言ったら、まず直した物が動いているかを見る（入れ替えが途中で止まっていないか）
- 直したことで、ほかの面が壊れていないかも見る（ほかの幅、ほかのページ、ほかの端末）

## 遅さ

- 直す前に基準の数字を取る。直した後に、同じ方法で取る
- 測る条件を、本人の使い方に合わせる（起動直後でなく使っている最中、Debug でなく Release、本物のデータの量）
- 数字を言う前に、何が律速しているかと、測っているものが本当にその仕事か（キャッシュ、ウォームアップ、エラーで早く返っていないか）を確かめる
- 原因の候補は、1つずつ外して測る。まとめて入れると、どれが効いたか分からない
- 安い順に試す: やらない → 二度やらない → 減らす → 後でやる → 見えない所でやる → 並べてやる → 安くやる。目標に届いたら止める

## 出力

1. 何が壊れていたか（利用者から見て）
2. 原因（最初に間違った場所。壊したコミットが分かれば、それ）
3. 直したこと
4. 確かめたこと: 直す前の再現の出力と、直した後の同じ出力を、そのまま並べる。確かめられなかった面

## 実例

自分のリポジトリで実際に起きたこと。数字とコマンドは当時のまま。

### 面が違った

- **作った場面で通り、実機で外れた**（2026-09、Sagashi）。「UI テストでタップを確かめた」と報告して実機に入れると、
  「見つけたタップしても何も起きない」と返ってきた。UI テストは対象を画面の中央に止め、建物も無い場面だった。
  判定を「画面上 22pt 以内で、遮られていない」に変え、実機のタップごとのログ（`対象 7pt → 見つけた`）で確かめた。原因は「未確定」と書いた
- **本人が打つコマンドで確かめていなかった**（2026-10、仕事の Web アプリ）。足した起動スクリプトを `next start` でしか試さず、
  本人の `next dev` で `--env-file= is not allowed in NODE_OPTIONS` が出た（`next dev` は node の引数を子プロセスの `NODE_OPTIONS` に移す）。
  2回目は、そのコマンドで起動 → curl → 止めてポートが空くまでを確かめた
- **別のプロジェクトのサーバーが答えていた**（2026-07、tcg-saas）。ポート 8787 で別プロジェクトの `wrangler dev` が動いていて、200 が返った。
  `/health` の `"service":"synch-api"` がディスクのコードと違うことで気づいた
- **本人の設定のせいにした**（2026-09、portfolio）。「ロゴが動的じゃない」に、視差効果を減らす設定を切るよう案内した。設定のまま回るように直した
- **本人の画面に合成の入力を送った**（2026-09、lr）。確かめのために本人の画面へ合成クリックと Esc を送り、2回止められた。
  最後は「画面は自分で確かめるから、残りを進めて」と言われた

### 証拠で絞った

- **計測を足して、原因を数字で見た**（2026-09、lr のスナップ）。合成ドラッグで窓は動くのに、スナップのログが出ない。
  時刻つきで並べると `264ms ax.x=300 server.x=288 cursor.x=576` で、AX から読む窓の位置が遅れていた。ウィンドウサーバーから読むように直した
- **独立した源と突き合わせた**（2026-09、lr のネットの累計）。`netstat -ib` が 10,283,094,716 バイトのところ、
  `NET_RT_IFLIST2` は 1,693,167,616 を返していた。ifmib に替えると1バイトまで一致した
- **観測が鈍いと「無い」に見えた**（2026-10）。コンテナのログの行数では問い合わせが0件に見え、ジョブの API で数えると5〜8件あった。
  レビューの道具は指摘が0件だと欄が空で、「まだレビューされていない」と読み違えた。
  リダイレクトする画面も中身を返す画面も 200 を返すので、状態コードでは見分けられず、本文で見分けた

### 前提を疑った

- **手当てが3回続いたら、土台を疑う**（2026-09、HTML の動きを動画に書き出す）。Chrome の `--screenshot` が終わらず300秒止まる
  → ファイルの大きさを見て閉じる → 自作の CDP クライアントにする → 1,255枚目で落ちる → 再起動を自作、と症状への手当てが続いた。
  「ほぼ1コア」と自分で書いたまま、25分の書き出しも続けていた。本人の「playwright を使えば？」で土台を替え、
  8並列で3分47秒になり、md5 も一致した
- **観測が仮説を区別しないなら、本物の面で通す**（2026-09、lr の Gatekeeper）。9/23 と 9/27 で `spctl -a -vv` の出力は同じ `rejected` だった。
  9/23 はこれを「『このまま開く』で通る」と読み、別の Mac で通していない手順を「想定どおり」と案内した。本人の返事は「このまま開くがでない」

### 隠し方の代償

- **版を留めた暫定策が、10日後に CI を止めた**（2026-10、仕事の Web アプリ）。依存の更新でテストが全部落ち、原因の版を突き止めて前の版に留めた。
  10日後、その留めのせいで `pnpm audit` が重大な脆弱性を見つけ、CI が止まった。根本の直しは、関係する2つを両方上げることだった
- **「直っていない」の正体は、直した物が動いていないことだった**（2026-09、lr）。`./install.sh >/dev/null 2>&1` が途中で止まり、
  古い版のまま確かめていた。`pgrep` が空で、`strings` に新しい文字列が0件だったことで気づいた

### 遅さ

- **測った条件と使い方が違った**（2026-09、Sagashi）。「Steady 60 fps」と報告したのは起動直後20秒の測定で、本人が遊んだ間は同じログで 31.6fps だった。
  切り分ける前に色見本の1枚化・LOD・カリングを入れたが効かなかった。`-noShadows` などで1つずつ外すベンチを実機で回して、影が主因と分かった。
  影の距離を 250m → 150m にすると、カメラ距離 40/90/150m の fps が 60/48/40 → 60/60/59 になった。惑星を作る時間は Debug 1349ms、Release 59ms
- **提案を実測で確かめた**（2026-10、CI）。98回・1,161分を測ると、提案されたジョブの統合では1回あたり1〜2分しか減らない。
  最大の無駄は、AI 自身の docs だけの push（26回・352分）だった
- **見積もりの道具は、本物の代わりでしかない**（2026-10、このスキルを作ったとき）。`claude plugin details` は、pstack を入れると
  常に約 4,748 トークン増えると見積もった。`/context` で実際に測ると、増えたのは約 200 だった

## 出どころ

手順は pstack（Lauren Tan、MIT）の bug-fix と perf-issue の playbook、principle の fix-root-causes・attack-the-premise・
prove-it-works・explain-the-number から、既定の振る舞いを変える部分だけを取った。https://github.com/cursor/plugins/tree/main/pstack
実例は、自分の Claude Code の会話履歴（2026-07〜10）から拾った。

## 確かめたこと（2026-10-23）

Opus 5.5（xhigh）に `claude -p` で同じ依頼を流し、スキルあり・なしで比べた（各1本、MCP なし、自動モード）。
題材は koimoyou の複製。見出しを 64px に固定したコミットの上に、無関係なコミットを1つ積み、見当の外れた報告をした。
「320 幅のスマホで見ると、最初の画面の見出しが左右の端までくっついて、文字が切れてる。.hero の overflow: hidden が怪しい気がする。直して」。
`overflow: hidden` を外すと、菱形の飾りでページが横に広がり、かえって悪くなる。

採点は外から、直した後の状態をビルドして、ヘッドレスの Chrome で 320・390・1280 幅の見出しの左右の端を測った。

| | 時間 | 費用 | 見当（`overflow: hidden`）の扱い | 直し方 | 採点 |
|---|---|---|---|---|---|
| なし | 2分7秒 | $0.61 | 菱形の飾りを切るのに要る、と読んで残した | `min(64px, calc((100vw - 40px) / 5.2))` | 320 幅で 23〜297 に収まる。390 幅以上は 64px のまま |
| あり | 2分56秒 | $0.82 | 実際に外し、ページが 434px に広がるのを見てから残した | `clamp(36px, 17vw, 64px)` | 320 幅で 21〜299 に収まる。390 幅以上は 64px のまま |

- どちらも、直す前に 320 幅で測って再現し（-3.2〜323.2）、原因のコミットを特定し、見当を退け、大きくした意図を残して直し、
  直した後に幅を変えて測った。手順の大部分は、Opus 5.5 には当たり前だった
- スキルで変わったのは確かめ方。見当を推論でなく実験で退け、本番と同じ配信（`cf-wrangler dev`）で測り、3ページを8つの幅で調べた
- 時間と費用は1.3〜1.4倍。本数が少なく題材も1つなので、傾向どまり
