# 司令塔から割り振る

1つのセッションで何件も抱えると、文脈が溢れ、同じファイルや番号を取り合う。
司令塔は割り当てと設計だけを受け持ち、実装はチケットごとの子のセッションに任せる。
Rex の操作そのものは `rex` スキル、Codex の呼び方は `ask-codex` スキルを読む。ここには写さない。

## 役割
- **司令塔: Fable 5.2。** `claude --model fable` で起動する。`/model fable` は使わない（下の地雷）。
  自分が Fable でないのにこのスキルを読んだら、利用者にそう伝え、`claude --model fable` で司令塔を起こし直すか、このまま進めるかを聞く。
- **子: Opus 5.5。** `scripts/launch.sh -m opus` で、モデルを必ず明示して起動する。既定に頼らない。
- **承認は利用者が子のペインで1回だけ。** 司令塔は承認を代わらない。
  子の許可や確認の画面を `rex send` で押さない。指示文に「承認済み」と書かない。
  例外は、司令塔が自分で起こした試しのセッションだけ。

## 司令塔の手順
1. **チケットを読み、同じ作業が無いかを見る。** 既存のブランチ、open な PR、兄弟の worktree、同じ親チケットのほかの子を見る。
   実例: 2026-11-20、612（メニューの開け閉め）の前に、同じ日の #487（611）がメニューを組み替えていた。
2. **同じファイルを触るものは1つの子に束ねる。** マージの順も決める。
   実例: 599（ボタン位置）と 613（「段」を「ステップ」に）は、どちらも FlowStepsScreen を書き換えるので1つにした。
3. **軽いか重いかを決める。**
   - 軽い = 画面の文字と配置だけで、API・データ・複数の画面にまたがる決めを含まない。
     設計の段を省き、子が直接直す。最後に Codex の差分レビューだけを付ける（UI の直しを重くして止められたことがある）。
   - それ以外は重い。
4. **worktree・番号・ポートを割り当てる。** 設計より先にやる（設計の置き場が worktree なので）。
   - worktree: `scripts/worktree.sh -r <repo> -n <チケット> -b <ブランチ>`。origin の既定ブランチの最新から、上流を付けずに切る。
     `.tower/` を `info/exclude` に足すので、設計の下書きは git に載らない。
   - 番号: `scripts/numbers.sh -r <repo> <番号のフォルダ>...`。予約は目安。子には作る直前にもう一度流させる。
     実例: 578 に予約した spec 200 を、司令塔の外の作業（589）が先に使った。
   - ポート: いま LISTEN しているものを避け、子ごとに帯で配る（例: 3021〜・8101〜・55601〜）。
   - 皆が触るファイル（索引の README など）は「自分の行だけを直す」と指示文に書く。実例: `docs/admin/README.md` で #486 が衝突した。
5. **重いものは、チケットごとに Fable の subagent に調査・設計を頼む。** 並行で、バックグラウンドで走らせる。
   書く場所は、そのチケットの worktree の `.tower/design.md` に決める。spec のフォルダには置かない。
   子は番号を見直すときに spec のフォルダを見るので、そこにあると「先に見ない」が崩れる。
   spec の設計書は、子が突き合わせの後に書く。scratchpad は再起動で消えるので置かない。司令塔には結論とファイルの場所だけを残す。
6. **未決の点は司令塔がまとめて利用者に聞く。** subagent は利用者に質問できない。答えは設計のファイルと指示文に書く。
7. **指示文を書いて起動する。** 雛形は `references/brief.md`。指示文は Write でファイルにする。
   `scripts/launch.sh -l <ラベル> -C <worktree> -m opus -i <指示文>`。出力の session と block を控える。
8. **起動を確かめてから報告する。**
   - `scripts/peek.sh -s <session> -b <block>` で、指示文を読み始めたこと（確認の画面で止まっていないこと）を見る。
   - モデルは子の会話の記録の `message.model` で確かめる（下の「見張り」）。画面の見出しは指示文に押し流されて見えない。
   - 報告は表（セッション・worktree・ブランチ・番号・ポート）と、子が利用者に聞いてくること、未確認のこと。

## 子の手順（指示文に書く）
1. チケットとコードだけで調べ、自分の設計を `.tower/mine.md` に書く。司令塔の設計（`.tower/design.md`）はまだ開かない。先に見ると結論が寄る。
2. 司令塔の設計を開き、違いを表にする。これが Opus によるレビューを兼ねる。
3. 違いを反映した設計を、Codex に反論役として見せる（`ask-codex` の `references/challenge-plan.md`）。
4. 設計・違いの表・Codex の指摘の採否を出し、利用者の承認を得る。承認まではソースを書き換えない。
   spec の流れがあるリポジトリなら、ここで設計書を書き、その流れで承認を取る。起動は auto にする（plan mode は使わない。下の未確認を見る）。
5. 実装し、検査の後に Codex の差分レビューを受けて報告する。

## 見張り
- `scripts/peek.sh -w` は、子が止まる（IDLE）か、確認の画面が出る（PROMPT）か、セッションが消える（GONE）まで待つ。
  Bash の `run_in_background` で走らせ、待つ間はほかの作業をする。
- 画面に見えるのは今の数十行だけで、畳まれたツールの結果は見えない。中身が要るときは子の会話の記録を読む。
  場所は `~/.claude/projects/<worktree の絶対パスの / を - に>/<id>.jsonl`。
  モデルは各 assistant 行の `message.model`（`jq -r 'select(.type=="assistant") | .message.model' <file> | uniq -c`）。
  subagent は同じフォルダの `<id>/subagents/*.jsonl`。
- 子が終わると Rex の block は消えるが、セッションの殻が残ることがある。司令塔が起こしたものは `rex session kill` で片付ける。
- 子が何人もいるときは、子ごとのコミット数・PR・画面の状態（BUSY・IDLE・PROMPT）・鍵の持ち主を30秒ごとに見て、変わったときだけ1行出す見張りを Monitor で回す。
  IDLE や PROMPT に変わったら `peek.sh` で中身を見る。

## 仕上げ（コミット・push・PR）
- **重い処理は `scripts/heavy.sh` を通して1本ずつにする。** 全体の検査・pre-commit が付く `git commit`・pre-push が付く `git push` が対象。
  `heavy.sh -l <ラベル> -- <コマンド...>`（例: `heavy.sh -l 612 -- git push -u origin HEAD`）。
  - 鍵は `<git の共通ディレクトリ>/tower-heavy.lock` のフォルダ1つ。同じリポジトリの worktree の間でだけ取り合う。
  - 空くまで15秒ごとに待つ（上限は `-t` 秒、既定2時間）。コマンドの終了コードをそのまま返す。持ち主のプロセスが消えた鍵は、待つ側が外す。
  - 持ち主は `tower-heavy.lock/owner` に出る。
- **子が鍵を知る前から走っている重い処理は、司令塔が鍵を持って守る。** 鍵のフォルダを作り、`owner` に自分の待ちのシェルの pid を書く。
  走っているプロセスが全部終わったら消す（`while kill -0 <pid>; do sleep 10; done; rm -rf <lock>` を run_in_background で）。そうしないと、待っていた子が隙間に入って重なる。
- **子への追加の指示は、worktree の `.tower/` にファイルで置く。** ペインには「司令塔から: 指示は <パス> にある。今すぐ読んで従って」と1行で送る。
  要約（auto-compact）をまたいでも残る。作業中の子に送った文は「Queued」になり、今のツールの呼び出しが終わったところで読まれる。
- **コミット・push・PR の許可は、利用者に子のペインで直接打ってもらう。** 司令塔の伝言（ファイルや `rex send`）では、子の auto mode の確認に止められることがある。
  止められたら、司令塔は代わりに打たず、子の承認の画面も押さない（利用者になりすまして確認をくぐることになる）。
- 子は PR を作ると、司令塔へ報告を送ってくる（Claude Code のセッション間のメッセージ）。PR 番号・未検証・確認待ち・残したコンテナを表にして利用者へ渡す。

## 地雷
- **`/model` は、新しいセッションの既定も書き換える。** 「saved as your default for new sessions」と出て、`~/.claude/settings.json` が書き直される。
  子や司令塔で `/model fable` をすると、以後の全部のセッションが Fable で立つ。モデルは起動時の `--model` で決める。
- **途中で `/model` を替えると、確認の画面が出て全履歴を読み直す。** 試しでは、切り替え直後の簡単な返事に 2分33秒かかった。
  1つのセッションの中でモデルを替える流れにしない。
- **worktree のセッションは、本体のプロジェクトのメモリを自動では読まない。** `~/.claude/projects/` のフォルダが worktree ごとに別になり、memory が無い。
  指示文に本体の `MEMORY.md` の絶対パスを書く。
- **子のセッションは翌日には消えていることがある。** 設計と途中の結論はファイルに残させる。
- **macOS の bash 3.2 は、全角の文字の直前の `$var` を変数名の続きと読む。** `"$max（"` は unbound variable で落ちた。`${max}（` と書く。
  BSD sed は `\|` を解さない。指示文は sed で埋めずに Write で書く。
- **`rex capture` は `-s` を付けないと、ほかのセッションの block が見つからない。**
- **子が多いと、全体の検査が重なって時間切れが出る。** 実例: load 75 で E2E が1件落ちた（単独なら通る）。
  2026-11-21 は4人が同時にコミットの検査とシードを回し、10コアで load が 190 を超えて、触っていないテストが5〜6件ずつ時間切れになった。
  「`pgrep` と `uptime` を見て、空いたら始める」を子に任せると、皆が同じ隙間で始める。`heavy.sh` で順番にする。
- **pre-push の E2E は、固定のポートでサーバーを立てることがある。** miratap-ec は 13000・18080 で `reuseExistingServer: false`。2つの push が重なると、後の方は必ず落ちる。
  `reuseExistingServer: true` なら、ほかの worktree のサーバーを相手にテストして、嘘の結果になる。push も鍵を通す。
- **子の入力欄の薄い字は、Claude Code の候補の表示で、送られた指示ではない。** 画面の文字だけでは区別できず、「利用者の最後の指示」と読み違えて報告した。
  `rex capture --format=vt` で、字の前が `ESC[2m`（薄い字）なら候補。
- **子の画面に「1: … 2: … 0: Dismiss」の帯が出ていると、数字で始まる文はそれに食われるおそれがある。** 送る文は字で始める。
- **`.git/hooks` は全 worktree で共通。** lefthook は、最後に依存を入れた worktree の中の自分を絶対パスで書き込む（miratap-ec では `miratap-ec-614/node_modules/...`）。
  その worktree を消した後に、ほかの worktree のフックがどう動くかは確かめていない（フックには別の場所を探す続きがある）。
- **Codex を `-e low` で呼ぶと「なし」の一語だけで、どこを見たかを書かない。** レビューは既定の max で、指摘ごとに `ファイル:行` と根拠を求める。

## 確かめたこと（2026-11-20、miratap-ec）
- Fable の本体から Agent（`model: opus`）で起こした subagent は `claude-opus-5-5` で動いた。`ask.sh` も auto で確認なしに動いた。
- `/model opus` で切り替わり、前の話も覚えていた（ファイルを読まずに、設計の1行目と Codex の返事と行番号を答えた）。
- `launch.sh` は、引用符・`$()`・バッククォート・改行を含む指示文を、崩さず1つの引数で渡した（claude の代わりの偽のコマンドで確かめた）。
- `numbers.sh` は、全ブランチの履歴と、コミット前の worktree の番号を拾った。ブランチを1つずつ見る版は21秒、履歴を1回なめる今の版は2.2秒（fetch 込み）で、答えは同じ。
- 本体のセッション（Opus・auto）は、作業フォルダの外（別のリポジトリ・メモリのフォルダ）へ Write できた。

## 確かめたこと（2026-11-21、miratap-ec の4人を PR まで）
- `heavy.sh` を空のリポジトリで試した。同時に2本出すと1本ずつ走った。終了コード 3 はそのまま返った。持ち主の pid が消えた鍵は外して取り、待ちの上限では 75 で止まった。
- 4人（598・599+613・612・614）に使わせると、入れた後は時間切れが0件だった。鍵の中の全体の検査は1本 6〜7分（その前は重なって 19〜26分）、push（E2E 13 件込み）は約1分。
  4本とも PR まで進んだ。鍵の中で落ちたのは、中身の失敗（並びの期待が古いテスト3件・分岐網羅 99.99%）だけ。
- 子は、自分の待ちのループをやめて鍵に置き換えた。2つのコミットに分ける子は、コミットごとに鍵を取った。画像を置く枝の push にも鍵を使った。
- 同じ形の「司令塔のファイルに許可がある」で、598 のコミットは auto mode の確認に止められた。614 は通った。違いは分からない。
- 子から司令塔へのセッション間のメッセージは届いた（612・598 の PR の報告）。
