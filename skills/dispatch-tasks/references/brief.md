# 子への指示文の雛形

司令塔が、子ごとにこの形でファイルを書く（Write で書く。sed で穴を埋めない）。`<…>` を埋め、要らない節は消す。
子はこの会話を知らない。チケットの本文・決まったこと・守ることを、ここに全部書く。

```markdown
<チケットのキー> を担当してください（<チケットの URL>）。<束ねたならその理由: 例「2つは同じ画面を触るので1つにまとめた」>

## チケット（<日付> 時点の本文）
<本文を写す。要約するなら要約と書く。本文が空なら空と書く>

## 進め方（重い作業）
1. まず、チケットとコードだけで調べ、自分の設計を worktree の `.tower/mine.md` に書く（`.tower/` は git に載らない）。
   司令塔の設計（`.tower/design.md`）は、まだ開かない（先に見ると結論が寄る）
2. 司令塔の設計を開き、自分の設計との違いを表にする（どちらが正しいかの根拠つき）
3. 違いを反映した設計を、Codex に反論役として見せる（ask-codex スキルの references/challenge-plan.md の手順）
4. 設計・違いの表・Codex の指摘の採否を利用者に出し、承認を得る。承認まで、ソースは書き換えない。
   リポジトリに spec の流れ（設計書 → テスト設計書 → 承認）があれば、ここで設計書を書き、その流れに合わせる
5. 承認の後に実装する。検査が通ったら、Codex に差分のレビューを頼み、採否を報告に書く

## 進め方（軽い作業: 画面の文字と配置だけ）
1. 調べて、直し方を短く利用者に出し、承認を得る
2. 直す。検査が通ったら、Codex に差分のレビューを頼む

## 決まっていること（司令塔が利用者に聞いた答え）
- <問い>: <答え>

## 用意したもの
- worktree: <絶対パス>（<基点のコミット> から）
- ブランチ: <名前>（上流は未設定。push は指示を受けてから）
- 番号の予約: <例: frontend spec 204・ADR 0065>。予約は目安。spec や ADR を作る直前に
  `~/.claude/skills/dispatch-tasks/scripts/numbers.sh -r . <番号のフォルダ>` を流して見直す
- ポート: <例: 管理画面 3021・API 8101・DB 55601>

## 同時に動いている作業
- <worktree>: <チケット>（<触る画面・ファイル>）
- マージの順は <順>。後ろの作業は、前の作業が入ったら rebase する。計画に、ほかの作業と重なりそうなファイルを書く
- <皆が触るファイル>: 自分の行だけを直し、ほかの行は動かさない

## 守ること
- 最初にプロジェクトのメモリを読む: <本体のメモリの MEMORY.md の絶対パス>
  （worktree のセッションからは自動で読まれない）
- <リポジトリの決め事をメモリから写す: Node の版・ロケール・検査の回し方など>
- 全体の検査は最後に1回だけ。走らせる前に `pgrep -fl 'vitest|runChecks'` と `uptime` で、ほかのセッションと重ならないかを見る
- コミット・push・PR・チケットの状態の変更は、その都度利用者の指示を受けてから
- 設計と途中の結論はファイルに残す（セッションは翌日には消えていることがある）
```
