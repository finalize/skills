## 確かめたこと（2026-11-21、同じリポジトリで4人を PR まで）

- 4人を PR まで回すと、皆が同時に全体の検査を回して負荷が 190 を超え、時間切れが出た。そこで `heavy.sh` を足した。
- `heavy.sh` を空のリポジトリで試した。同時に2本出すと1本ずつ走った。終了コード 3 はそのまま返った。持ち主の pid が消えた鍵は外して取り、待ちの上限では 75 で止まった。
- 4人（うち1人は2件を束ねた）に使わせると、入れた後は時間切れが0件だった。鍵の中の全体の検査は1本 6〜7分（その前は重なって 19〜26分）、push（E2E 13 件込み）は約1分。
  4本とも PR まで進んだ。鍵の中で落ちたのは、中身の失敗（並びの期待が古いテスト3件・分岐網羅 99.99%）だけ。
- 子は、自分の待ちのループをやめて鍵に置き換えた。2つのコミットに分ける子は、コミットごとに鍵を取った。画像を置く枝の push にも鍵を使った。
- 同じ形の「司令塔のファイルに許可がある」で、ある子のコミットは auto mode の確認に止められた。別の子は通った。違いは分からない。
- 子から司令塔へのセッション間のメッセージは届いた（2人の PR の報告）。

## スクリプトの見直し（2026-11-21）

レビューで見つかった点を直し、リポジトリの `tests/` で固定した（偽の rex・偽の claude・使い捨てのリポジトリ）。

- `numbers.sh`: リポジトリの根より下のディレクトリから `-r .` で流すと、履歴の分が丸ごと抜けて、使用済みの番号を「次」と返した
  （ほかのブランチに 203 があるのに「次は 203」。終了コードは 0）。根に寄せてから数える形にした
- `heavy.sh`: 持ち主が消えた鍵を2人が同時に外しにいくと、先に取り直した人の鍵を後の人が消して、2本が重なった
  （片方の `rm` を3秒遅らせて再現。自然な窓は約8ms）。外すのを1人ずつにし、その中で持ち主を読み直す。
  後始末は自分の鍵だけを消す。git の外では止まる（前は、現在地に鍵を作って素通りした）。
  止める合図（TERM など）を受けた包みは、中の処理が終わるのを待ってから、鍵を返して 143 で終わる（前は 0 で終わった）
- `heavy.sh` の知っている穴: 包みのシェルだけが SIGKILL されると、中の処理が生きていても次が入る。
  中の処理を `&` で起こして pid を持ち主に書けば見分けられるが、ジョブ制御の無い bash では `&` の子は SIGINT を無視するので、形は変えていない
- `peek.sh`: 画面が空だと終了コード 1 だった。子の出力の本文に "Do you want" があると PROMPT と読んだ。待っている途中の GONE は終了コード 0 だった。
  PROMPT は、画面の下に確認の文と番号つきの選択肢が組で出ているときだけにした（本物の確認の画面では未確認）
- `worktree.sh`: `info/exclude` が改行で終わっていないと `*.swp.tower/` のようにつながり、`.tower/` が git に見えた
- auto memory の場所: 使い捨てのリポジトリとその worktree で `claude -p` を起こして聞くと、どちらも本体のフォルダの memory を答えた
  （Claude Code 2.1.330）。前の地雷「worktree のセッションは本体のメモリを読まない」とは食い違う。
  確かめたのは場所までで、`MEMORY.md` の中身が読み込まれたかは見ていない。対話のセッションでも見ていない
