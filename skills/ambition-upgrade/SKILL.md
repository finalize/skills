# 依頼を野心的にする

既定のままだと、AI は依頼の文面の範囲で仕事をする。「四半期の数字を更新して」なら、よくできた資料は作るが、
依頼そのものは問い直さない。このスキルは、実行する前に依頼を3方向から見直す。

見直すのは**依頼の中身**で、量ではない。ページ数や作業量が増えるだけなら採用しない。

## 向くとき・向かないとき

- 向く: 資料、分析、調査、自動化、運用の改善。目的や成果が先にある仕事。
  会議で議論する対象になる仕事は、特に高度を上げる価値が高い。
- 向かない: 創作や好みの仕事（高度は上げない）。一文の質問。誤字の修正のような小さな編集。
  速く終わらせたいだけの依頼（速度の話はこのスキルの対象外）。
- 「事業で利益を出して」のように目的だけを丸投げするのは、まだ手に余る。
  できる範囲を見極め、足りない環境（データ、実行、検証）を明記する。
- かかるもの: 資料の骨子で測ると、時間は3〜5倍、費用は2.5〜4倍かかった（下の「確かめたこと」）。
  急ぐ依頼には使わない。

## 手順

### 0. 依頼と使える環境を確認する

依頼、成果物、触れる素材（ファイル、コネクタ、ブラウザ、実行環境）を確かめる。
質問は最大1つ。それ以外は妥当な前提を置いて進め、前提は冒頭に書く。

### 1. 高度: その先のゴール

- この成果物が完成したら、次に何が起きてほしいのか
- 最終的に変えたい結果は何か（ゴールの先のゴール）
- 個別の作業ではなく、その結果を保つ仕組みにできないか

例（四半期レビュー）: 数字を更新するだけ → 「何が変わり、なぜ、どうすべきか」を聞く
→ 最も急ぐ決定を3つ選び、賛否の論点まで作る
→ レビューの目的（問題の早期発見、人と金の再配分）から、四半期の資料に代わる仕組みを設計し、
過去のデータで有効性を示し、1四半期並行して動かす。

上げるのは、渡された権限と期間の中で実行できるところまで。仕組みの置き換えや並行運用のように、
期間・権限・他の人が要るものは提案に留める。例の最後の段なら、設計と過去のデータでの検証までを成果物に入れ、
動かすかどうかは依頼主が決める。

人を介さずに回る仕組みにするときは、先に環境を整える。例: アプリを落ちない状態に保つ仕事なら、
落ちた記録を取れること、版とコミットを対応付けられること、各 OS の実機で再現して直ったと確かめられること。
頼まれていない環境づくりも、提案から始める。

### 2. 深さ: 第一人者のやり方

次の4点に答えてから、依頼を書き直す。

1. その分野の第一人者は、依頼されていないことで何をするか
2. 加工済みの資料ではなく、最も生に近い素材は何か
3. 使う手法とツールは何か。表で済ませず、データベースや統計モデルなど本物の道具を使う
4. 自分と依頼主以外に、結果が正しいと示すものは何か

さらに次を問う:

- 社内で通説になっていることを、生データから反証できるか試したか
  （例: 「離脱は初期設定でつまずくことが原因」を、生データから再現できるか試す）
- まだ知られていない兆候や盲点を探し、見ていないデータで予測できると確かめられるか
- 目標は緩すぎないか。難しくても具体的な数字を置く（表示を10秒から5秒ではなく、200ms など）。
  別のエージェントに頼むときは、その数字のまま渡し、解ける前提で続けさせる。
  依頼主には、届いた数字をそのまま報告する。届かなかったものを「続ければ解ける」とは言わない

**自分で自分の出力を採点させない。** 実行して即座に結果が返る道具（テスト、計算、検証スクリプト）を外部の審判にする。
そういう道具が無いなら、無いと報告する。

### 3. 幅: 他分野の作業を借りる

1. 成果物の名詞を動詞に言い直す。「資料」ではなく
   「忙しい人に因果の話を信じてもらい、不確実な中で30分で決めてもらうこと」
2. その動詞に効く分野を3〜5つ挙げる（分析、編集、デザイン、反対意見を出す役など）
3. 各分野の人が**実際にやる作業**を割り当てる。並行して進められるものは分担する

**役を演じさせない。** 「空売り投資家として振る舞って」ではなく、「空売り投資家が自分の見立てを調べるやり方で、
この数字を調べて」と頼む。役を演じさせると、言葉づかいだけが変わってやり方は変わらない。
記録が妙になるだけで、結果は良くならない。

### 4. 強化した依頼を示して実行する

記事は人がモデルに頼むための手引きで、強化した依頼は人に返り、送るかどうかは人が決める。
このスキルではモデルが自分で広げるので、どこまで実行するかを分ける。

- 元の依頼と強化版の違いを3〜5行で示す
- 「もっと野心的に」のように頼まれて呼ばれたなら、強化版を実行する。
  ただし公開・送信のように取り消しにくいものは、いつもどおり実行の前に確かめる
- 自分の判断で呼んだなら、成果物（資料、分析、下書き）の中で深める分は実行してよい。
  外に作用するもの（定期実行の登録、常駐、送信、公開、他人の環境の変更）と、
  期間・権限・他の人が要るもの（仕組みの置き換え、並行運用）は、実行せずに提案として返す
- 依頼主が確認を望んだなら、どちらの場合もここで止めて確認を取る
- 実行したら、外部の検証で確かめられたことと、確かめられなかったことを分けて報告する

## 出力

1. 置いた前提
2. 3方向の見直し（各2〜4行。当てはまらない方向は「見直さない」と理由を一行）
3. 強化した依頼（実行せずに提案として返すものは分けて書く）
4. 実行の結果と、外部の検証で確かめられたこと・確かめられなかったこと

## 出どころ

出どころは Felix Rieseberg, How to be more ambitious: A tutorial for humans with models（2026-10-13）。
https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/
高度・深さ・幅の3分類と、各手法、プロンプトの型はこの記事のもの。
記事は速度（同じ仕事を速く終える）を含めた4分類だが、このスキルでは扱わない。

## 確かめたこと（2026-10-17）

Opus 5.5 に `claude -p` で同じ依頼を流し、スキルあり・なしで比べた（各1〜2本）。
題材は架空の SaaS の KPI 4四半期分の CSV。

| 依頼 | スキル | 時間 | 費用 |
|---|---|---|---|
| Node の LTS の版を聞く／CSV の月別集計／古いログを消すスクリプト | 呼ばれない | 差なし | 差なし |
| 四半期レビューの資料の骨子 | 2本とも自分から呼んだ | 80秒 → 250〜300秒 | $0.35 → $0.86〜1.13 |
| 「もっと野心的に」＋同じ骨子 | 呼ばれた | 104秒 → 479秒 | $0.42 → $1.59 |

- 骨子は、スキル無しでも決めること・仮説・確かめ方まで書けていた。スキルありで足されたのは、
  資料の数字 38〜55 か所を CSV から計算し直した照合、対立する仮説とそれを見分けるデータ、
  「全員が最安のプランでも純増 850 件なら +102万円のはず、実際は +30万円」という下限の議論、
  賛否つきの決めること。分量は2倍前後になった。
- 「もっと野心的に」では、スキル無しは「目標を野心的に」と読み、背伸びした目標を置いただけだった。
  スキルありは仕事の中身を深くした。90 の数字を照合し、照合の仕組みも数字を7か所書き換えて確かめ、
  自分の誤りを2つ見つけて直した。
- 四半期の資料に代わる仕組みは、どの回も提案で止まった。ただ、止まれとは書いていなかったので、手順1と4に足した。
- 本数が少なく題材も1つなので、傾向どまり。
