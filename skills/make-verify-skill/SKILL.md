# 確かめる手順をリポジトリに置く

既定のままだと、確かめる手段の無いリポジトリで AI は、ビルドと単体テストが通ったことをもって「動いた」と言うか、
「ブラウザで確認してください」と人に返す。どちらも、利用者が触る面では何も確かめていない。

このスキルは、起動・操作・証拠・後片付けの手順と、そのリポジトリで踏んだ罠を、`.claude/skills/verify-<名前>/` に置く。
読むのは次のエージェントで、そのアプリを見たことがないまま、作業の途中で読む。人向けの説明ではなく、その読み手に向けて書く。
リポジトリにコミットして、次のエージェントも人も同じ手順を使えるようにする。

## 向くとき・向かないとき

- 向く: 画面・CLI・API・実機のアプリがあって、変更のたびに動かして確かめたいリポジトリ。同じ確認を何度も手でしている。
- 向かない: ライブラリだけで、テストが利用者の使い方そのもののとき（effective-tests で足りる）。捨てる前提の試作。
- 頼まれずに自分で呼んだなら、作らない。「このリポジトリには確かめる手順が無い。make-verify-skill で作れる」と提案して、
  元の作業に戻る。作るのは大きな寄り道になる。
- かかるもの: koimoyou の LP で、作るのに約20分・約$4（スキルの有無で差は無かった。下の「確かめたこと」）。

## 手順

### 1. 人でなく、リポジトリに聞く

コードから答え、見ても分からないことだけ人に聞く。

- 面: 利用者が触るもの（Web、CLI・TUI、iOS、API）。いくつもあれば主なもの1つを決め、残りは書き留める
- 起動: リポジトリの dev コマンド（`package.json` の scripts、Makefile、README）。ポート、環境変数、初期データ、認証
- 操作: 既にあるもの（Playwright、XCUITest、curl で叩ける口）を先に使う。無ければ汎用の手（ブラウザ、tmux、HTTP）
- 観測: スクリーンショット、ログ、レスポンスの中身、終了コード、保存された中身
- 隔離: 2つ並べて動かせるか（ポート、データの置き場）。並べられないなら、そう書く。人が使っている実体は動かさない

そのままでは起動しないなら、先に直すか、どこで止まるかを正確に報告する。壊れた土台の上に書いた手順は、間違った手順を教える。

### 2. スキルを書く

`.claude/skills/verify-<名前>/SKILL.md` に、聞き取りで見つけた実物で書く。例の値を残さない。
frontmatter の `description` には、アプリの名前、面、いつ使うかを書く。frontmatter が無いとスキルとして読まれない。

- **起動**: 確かめ用に起動する正確なコマンドと、使える状態になった合図（ログの一行、画面の文字）。
  プロセスが応答しただけでは、使える状態ではない。空のデータから、移行と初期データを含めて使える状態まで。止め方も書く
- **診断**: 「この実体は動かす価値があるか」に答える、読むだけの確認を1つ。プロセス、版、ポートの持ち主、認証。
  様子がおかしいときは、まずこれを流す
- **操作**: このリポジトリの実際のセレクタとコマンド。座標やタブの順でなく、ARIA の名前、data 属性、画面の文字、URL の道筋
- **証拠**: 何を撮り、どこに置くか。利用者の道筋を通す（内部のセッターや、テスト専用の口は使わない）。
  操作と、その結果の状態の両方を残す。見た目だけでなく副作用（書かれたファイル、入った行、送ったメッセージ）も見る。
  dry-run は名前を信じず、何を飛ばしているかを観測する
- **後片付け**: 自分が起動したものだけを止める。プロセス名で kill しない。証拠は消さない（置き場所を書いておく）
- **補助スクリプト**: 置くなら実行権限を付け、呼び方を本文に書く。
  操作はできるだけスクリプトにする。エージェントの道具（ブラウザの拡張など）に頼ると、別のエージェントや CI から流せない

### 3. 機能の地図を作る

`features/README.md` と、利用者に見える機能ごとに1ファイル。まず上位の3〜5個から。
各ファイルは利用者の目線で、できること・辿り方・動かし方・罠の4節にする。実装の話は入れない。

初期データに前提が無くて通らない機能は、失敗と書き、理由を罠に書く。手順を弱めて通さない。

### 4. 渡す前に一度通す

書いた手順を最初から自分で流す。起動 → 診断 → 機能を1つ動かす → 証拠を撮る → 後片付け → 証拠が残っているかを見る。
後片付けが証拠まで消したら、この段は不合格。

落ちたら直して、そのたびに後片付けまで流す。落ちた試行がプロセスやポートを残さないように。
**一度も流していない手順は下書きで、渡すものではない。**
本物の代わり（コンテナ、手元の環境）で通したなら、本物では起きない手順を書き出す。そこは本物で流すまで未確認のまま。

### 5. 古くなったら直す

アプリが変わると、地図はその日から古くなる。直すときは:

- 機能ごとにソースを読み直して、地図との食い違いを探す。読むだけなので並行してよい
- 全部の機能を一度ずつ実際に動かす。ソースが合って見えても省かない
- 食い違いは3つに分ける。地図の書き間違い → 地図を直す／動くのに手順で動かせない → 手順を直す／
  アプリが壊れている → 地図を合わせず、不具合として報告する

## 罠

実際に踏んだもの。生成するスキルの「罠」に、当てはまる分を写す。

### iOS（Xcode 27・iOS 27、2026-09 Sagashi）

- 横向きの `XCTAttachment(screenshot: app.screenshot())` は壊れる（2622×1206 の中に、回転した正方形だけ）。
  UI テストを走らせながら、裏で `xcrun simctl io <udid> screenshot` を回して撮る
- `Logger.info` は残らない。起動する前に
  `xcrun simctl spawn <udid> log stream --level info --predicate 'subsystem == "..."'` を始めておく
- Xcode を更新した後の最初の `xcrun simctl` は、部品の導入で1〜2分かかる。裏で流す
- Xcode 27 では Simulator.app が DeviceHub.app に置き換わった。`open -a Simulator` は失敗する
- 実機は `xcrun devicectl device process launch --console --terminate-existing <bundle id>` で起動してログを読む。
  画面がロック中だと失敗するので、再試行で回す（7回止まった）。アプリへの引数は `--` の後ろに置く
- UI テストで作った場面（対象が中央に止まっている、建物が無い）で通っても、実機で外れる。タップの判定は実機のログで確かめる
- 性能は Release で測る（惑星を作る時間が Debug 1349ms、Release 59ms）
- `swift file.swift`（インタプリタ）はコンパイラごと落ちることがある。`swiftc file.swift -o x && ./x` にする
- USD に `metersPerUnit` が無いと 0.01 とみなされ、RealityKit もそれに従う（60 単位が 0.6 m）。大きさは見た目でなく数値で確かめる

### macOS のアプリ（2026-09 lr）

- 合成のクリックやキーは、本人が使っている画面に届く。本人の作業を2回止めた。試験用の窓を作り、
  「最前面が試験用の窓でなければ何もしない」ガードを付ける。許可のダイアログは本人に押してもらう
- `RegisterEventHotKey` で登録したホットキーは、合成キーを受けない（4通りの送り方で試した）
- `NSStatusItem` のメニューは、System Events の `menu bar 2` では取れない
- accessory のアプリでは、`frontmost` が別のアプリ（端末）を返す
- SwiftUI の `Picker` の `.disabled` は、AX からは enabled=true に見える
- 本物の Mac に無い条件（ノッチ）は、アプリの試験用の設定で作る（`defaults write … fakeNotch -bool true`）
- zsh では `log` が組み込みとぶつかる。`/usr/bin/log show --predicate …` と書く

### Web

- Claude in Chrome は、確かめに2回とも使えなかった。背景のタブでは requestAnimationFrame が0フレームで、
  `resize_window` も効かず innerWidth が 2320 のままだった。Playwright のスクリプトにする
- 画素まで合わせるとき（2026-10 koimoyou）: デザインの HTML は `file://` で、移植した版は本番と同じヘッダーで開き、
  同じ Playwright のスクリプトで 390×844・320×640・1280×800 のページ全体を撮る。sharp で RGB の差の和が30を超える画素を数えて 0 にした。
  整形の前後で innerText も比べる（HTML の中の改行は、日本語の文では空白になる）
- 横のはみ出しは `scrollWidth > clientWidth` だけでは見えないことがある。見出しを 64px に固定して 320 幅で左右の余白が消えても、
  `.hero` の `overflow: hidden` の中で切れるだけで、`scrollWidth` は 320 のままだった。幅ごとにスクリーンショットを撮って見る
- リダイレクトする画面も、中身を返す画面も、200 を返すことがある。状態コードでなく本文で見分ける
- スモークテストがログイン画面の 200 で全部通っていた。基準値との比較も、比べる対象が0件のまま成功していた。対象が0件なら落とす
- 同じポートで、別のプロジェクトのサーバーが答えていたことがある（`/health` の `service` がディスクのコードと違った）。
  起動したら、いま見ているコードの応答かを確かめる
- 本人の開発サーバーや、共有のエミュレータは使わない。壊して確かめる作業が共有のエミュレータを壊し、本人に見せる画面が15分正しくなかった。
  別の作業ツリー・別のポートで起動し、終わったら自分が開いたポートだけを止める
- コピーの機能は、`grantPermissions(["clipboard-read"])` を足して、クリップボードの中身まで読む
- AI が `next dev` を起動すると、CLAUDE.md が書き換わることがある（2026-10）。起動した後に `git status` を見る

### 差し替えと、デプロイの止め方（2026-10-23、このスキルを測ったとき）

- デプロイを止めるつもりの差し替えが効かず、測定の採点で本物の Cloudflare に2回公開した。`node_modules/.bin/cf` を
  記録だけする偽物に替えたが、pnpm が `run` の前に依存を入れ直して本物に戻していた（ログに `prepare$ vp config`）。
  採点の側には、無効なトークンを渡し忘れていた。架空の LINE の URL を載せた LP が数分公開され、本人の許可を取って Worker ごと消した
- 差し替えは、使われたこと（偽物の記録に残ったこと）を見てから、本物の認証情報がある場所で流す
- 認証は、環境変数の無効なトークンで先に切る。`cf` はログインより環境変数を優先し、`[9106] Authentication failed` で落ちる。
  一覧を読むだけのコマンドで、落ちることを先に確かめる

### Cloudflare Workers ＋ Vite+（2026-10 koimoyou）

- `_headers`（CSP など）と 404 は `vp preview` では効かない。本番と同じ形で見るのは `cf-wrangler dev`。`--ip` は使えない
- 公開 URL を見込みで書かない。最初のデプロイの出力で確かめてから設定に書く
  （見込んだサブドメインが引けず、OGP と canonical が他人のサブドメインを指すところだった）

### シェル（この Mac）

- zsh では、一致しないグロブ（`rm -f Foo.usd*`、`--include=*.swift`）で止まり、`&&` の後ろが走らない。グロブは引用するか、ファイル名を書く
- `| grep` や `| tail` をつなぐと、終了コードが消える（`xcodebuild … | grep` で2回）。`set -o pipefail` にするか、終了コードを別に見る
- zsh では、変数は空白で分かれない。`pnpm $step` が1語として渡り、偽の失敗になる。配列にする
- macOS に `timeout` は無い（exit 127）。`perl -e 'alarm 60; exec @ARGV' <コマンド>` で代える
- `grep` の正体が ugrep のことがある。日本語と `.{0,300}` で complexity limits に当たる。`/usr/bin/grep` か `rg` を使う
- `zsh -ilc` は親の PATH を引き継ぐ。新しい端末を再現するなら `env -i` から始める

1. 作ったファイル
2. 一度通した記録: 流したコマンド、証拠の置き場所、落ちて直したところ
3. 確かめられなかったこと: 届かなかった機能と、足りなかった前提

## 確かめたこと（2026-10-23）

Opus 5.5（xhigh）に `claude -p` で同じ依頼を流し、スキルあり・なしで比べた（各1本、MCP なし、自動モード）。
題材は koimoyou の複製で、依頼は「LP を変えたときに、AI が自分で起動して確かめられるように、確かめる手順をスキルとして作って」。

作られたスキルを、何も知らない別の `claude -p` に渡して再生した。直前のコミットに崩れを2つ仕込み、「壊れたところが無いか確かめて」と頼んだ。
仕込んだのは、見出しを 64px に固定して 320 幅で左右の余白が消える崩れ（テストは通る）と、知らないパスが 404 でなく
200 で LP を返す設定の変更（テストは通る）。

| | 作る時間 | 作る費用 | 作ったもの | 再生の時間 | 再生の費用 | 仕込んだ崩れ |
|---|---|---|---|---|---|---|
| なし | 23分 | $4.18 | `drive.ts` 1本と SKILL.md（114行）。6か所壊して効くのを確かめた | 4分29秒 | $0.75 | 2つとも見つけた |
| あり | 19分 | $4.03 | `verify.sh`・`doctor.sh`・`drive.ts`・`ios.sh`、機能の地図（5つ）、SKILL.md（144行）。4か所壊して確かめた | 3分28秒 | $0.72 | 2つとも見つけた |

- 差は出なかった。スキル無しでも、作った手順を一度流し、わざと壊して効くのを確かめ、自分が起動したものを止めていた。
  再生ではどちらも、ひとつ前のコミットにも同じ確かめを流して比べた。手順の節（1〜4）は、Opus 5.5 には当たり前だった
- 違いが出たのは形だけ。ありは機能の地図・診断・iPhone の Safari での撮影まで作り、なしは CLAUDE.md の決まり（折り返し、44px のボタン、
  Tab のフォーカス）を細かく確かめる手順にした。なしの手順は、今の LP の本物の不具合（320 幅で「例で｜す。」と折れる）を見つけた
- 測っていないこと: 頼まれていないときに提案するか（description で呼ばれるか）と、罠の節の知識が効く題材（iOS、macOS のアプリ）
- なしの再生だけ、仕込んだ変更のコミットがコミット前のフックで失敗し、未コミットの変更として渡った。エージェントはそれに気づいて確かめており、結果は変わらない
- 本数が少なく題材も1つなので、傾向どまり
